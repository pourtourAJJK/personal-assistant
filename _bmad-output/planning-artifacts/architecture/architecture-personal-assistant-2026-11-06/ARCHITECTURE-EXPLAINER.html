1这个程序是什么

QuickTask 是一个命令行任务管理工具：添加任务（标题 / 分类 / 截止日期）、查看全部、标记完成、删除、查看统计。数据保存在本地 data/tasks.json，没有任何网络、账号或第三方依赖 —— 只需一个 Python 3 环境。

V1 有意保持功能克制（见 PRD Non-Goals），把架构重心放在清晰的分层上：这是为了将来迁移到 React + Django Web 架构时，业务逻辑层可以被直接复用。

2分层架构与依赖方向

为什么这样分：每一层只能调用紧邻的下一层。cli.py 永远不直接触碰 tasks.json；storage.py 不 import 项目内任何模块。将来做 Web 版时，task_manager.py 几乎原样成为 Django 的 service 层，storage.py 换成 ORM，只有表现层需要重写。

3七条架构决策（AD-1 ~ AD-7）

每条决策都遵循「绑定什么 → 防止什么 → 规则是什么」的结构。这里是摘要，完整规则见脊柱文档。

决策一句话规则它防止的事故
AD-1 分层依赖方向依赖只能向下：cli → task_manager → storageCLI 与存储实现耦合；换存储方案时全项目返工
AD-2 唯一实体 Task6 个固定字段的 dict，仅在 task_manager 中构造与校验同一实体在不同模块里长成不同形状
AD-3 存储独占 + 原子写只有 storage 碰 tasks.json；缺文件返回 []，保存 = 临时文件 + os.replace，强制 UTF-8多条读写路径互相覆盖；首次运行崩溃；写一半断电留半个文件；中文乱码
AD-4 直写 + 无缓存每次操作现读磁盘，变更后立即保存；任何模块不持有任务缓存缓冲写导致崩溃丢数据；统计读到过期缓存
AD-5 ID 生成契约TASK + 至少 3 位零填充，max+1，删除后不复用ID 冲突；删了 TASK003 又冒出一个新 TASK003
AD-6 错误边界 + 消息归属storage 抛异常 → task_manager 转结果元组 → cli 只显示；操作结果文案归 task_manager，交互提示归 cli原始异常直接砸到用户脸上；两套代码各自发明文案
AD-7 损坏保护文件损坏时所有操作一律失败返回，永不写回损坏文件被一次「添加任务」整个覆盖，历史数据全灭
AD-7 为什么重要：假设 tasks.json 被手动编辑坏了。如果没有这条规则，用户选「添加任务」时，程序可能以空列表继续运行，然后 save_tasks() 把坏文件整个替换成只含一条新任务的数组 —— 全部历史数据无声消失。AD-7 + AD-4 组合把这个路径彻底堵死：损坏状态下连写操作都不许走到 save。

4模块接口契约（谁和谁怎么对话）

脊柱把每个公开函数的签名和返回值形状都钉死了，两个开发者不可能各自实现出对不上的接口：

# storage.py — 仅两个公开函数
load_tasks()  -> list          # 文件缺失/为空 → []；损坏 → 抛异常
save_tasks(tasks: list) -> None # 原子写，自动建 data/ 目录

# task_manager.py — 全部返回 (success: bool, message: str, data) 元组
add_task(title, category, due_date)  -> (True, 成功文案, 新ID)
view_tasks()                         -> (True, "", 任务列表)
get_task(task_id)                    -> 任务dict 或 None（删除前展示详情用）
complete_task(task_id)               -> 已完成时 (True, "already completed", None)
delete_task(task_id)                 -> (True, 删除成功文案, None)
get_statistics()                     -> (True, "", {"total", "pending", "completed", "completion_rate"})

一次「删除任务」的完整旅程

  1. cli 收集 ID，调 task_manager.get_task("TASK003") 拿到详情并展示
  2. 用户确认 y → cli 调 delete_task("TASK003")
  3. task_manager：load_tasks() 现读磁盘 → 从列表移除 → 立即 save_tasks() 原子写回
  4. 返回 (True, "Task TASK003 deleted successfully!", None) → cli 原样显示，回到主菜单
  5. 任一步出错：损坏 → (False, 损坏文案, None)，且不发生任何写盘；ID 不存在 → (False, "Task not found.", None)

6明确推迟的事（以及为什么现在不做没关系）

  • 任务编辑 / 搜索 / 分类管理 — PRD 明确划出 V1 范围。现有分层下，它们只是 task_manager 新增函数 + cli 新增提示，零结构改动。
  • Web 迁移（React + Django，V2.0） — 这是整个分层的存在理由：业务层可整体平移。
  • 逐条任务 schema 校验 — V1 只把「合法 JSON 数组」作为损坏边界，字段级污染推迟到 V1.1。
  • 并发锁 / 日志 / 打包 / i18n / 测试框架选型 — 单用户单进程的本地 CLI 暂时都用不上；接口不变的前提下随时可加。
评估要点：本架构的全部约束（7 条 AD + 接口契约）都可以在代码里逐条机械验证 —— 检查 import 语句即验证 AD-1/AD-3，检查 save 调用点即验证 AD-4，检查 except 子句即验证 AD-6/AD-7。可验证性本身也是设计目标之一。
